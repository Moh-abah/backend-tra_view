## ⚡ إصلاح أداء جوهري (جلسة التمرير اللانهائي البطيء)

اكتشف وكيل الفرونت أن صفحات التمرير للخلف `?before=` تأخذ **22-56 ثانية** لكل صفحة على سيرفر الإنتاج.

### السبب الجذري — كاش لا يتراكم أبداً
في `get_historicalcandl` كان فلتر `merged["time"] <= end_ms` (المخصص لإسقاط الشمعة غير المغلقة) يُطبَّق على **الدمج الكامل** قبل الحفظ:
1. الصفحة الأولى (الطرف الحديث) → يُخزَّن الكاش الحديث ✓
2. صفحة تمرير قديمة → يُدمج القديم مع الكاش الحديث ثم **يُفلتر كل شيء ≤ نهاية النافذة القديمة** → تُحذف كل البيانات الحديثة → يُحفظ الملف بالنافذة القديمة فقط
3. **النتيجة:** كل صفحة تمرير تحذف ما قبلها وتعيد جلب ~6000 شمعة من Binance من الصفر، ومع rate-limit (429) على سيرفر إنتاج عليه مستخدمون متعددون → 22-56 ثانية للصفحة

### الإصلاح
فلترة **الدفعات المجلوبة فقط** (إسقاط الشمعة الحية عند الطرف) مع الإبقاء على الكاش السابق كاملاً — الكاش يتراكم الآن في الاتجاهين ويُحفظ دائماً.

### نتائج القياس بعد الإصلاح (محلياً)

| الحالة | قبل | بعد |
|---|---|---|
| صفحة تمرير جديدة (باردة) | 22-56s (إنتاج) | **0.12-0.36s** |
| نفس الصفحة مرة أخرى | إعادة جلب كامل | **0.03-0.19s من الكاش (صفر شبكة)** |
| تراكم الكاش | لا يتراكم (يُكتب فوقه) | 6260 → 11260 → 16260 شمعة ✓ |
| سلامة البيانات عبر الصفحات | — | 15000 شمعة متصلة: صفر فجوات/تكرار ✓ |

**أحجام الصفحات المقاسة (دافئ/بارد):** 500 → 29/205ms · 1000 → 45/145ms · **2000 → 82/183ms (الموصى به للفرونت)** · 5000 → 187/361ms

> مع هذا الإصلاح أي حجم صفحة حتى 5000 سريع — لا حاجة لتغيير الفرونت. التمرير المتكرر لنفس المنطقة يصبح فورياً بالكامل، والكاش ينجو من إعادة تشغيل الحاوية (حجم Docker مسمى).

## 🔧 إصلاحات الجولة الأخيرة (2026-10-29 — جولة 2)

### 1) مؤشر `rsi_1h_momentum` — كان يفشل ويعود NaN مع Traceback في كل طلب
الواجهة ترسل `{"name": "rsi_1h_momentum"}` إلى `/api/v1/indicators/signals` والسجل لا يملك هذا الاسم:
`Indicator 'rsi_1h_momentum' not found in registry` + قيم NaN + طوفان Traceback.
**الإصلاح من طبقتين:**
- تسجيله كمؤشر حقيقي (RSI فترة 14، فئة momentum) — قيمه تُحسب فعلياً (720/720 قيمة صالحة محلياً) ويظهر في `/available` و`/params`
- شبكة أمان عامة `resolve_name` في registry: أي اسم غير مسجل يُحلّ تلقائياً (حذف لواحق زخرفية مثل momentum/trend/fast → `rsi_1h_momentum` → `rsi_1h`) مع تحذير واحد نظيف في السجل بدل Traceback

### 2) الجذر الحقيقي لصفحات `before=` البطيئة: حظر Binance المؤقت (HTTP 418/429)
القياس المباشر أكد: كل دفعة klines تواجه 418 (حظر IP مؤقت) تحرق **4 محاولات × 15 ثانية انتظار متسلسلة**، وكل الدفعات المتوازية (7 لكل صفحة) تضرب الحائط معاً → 30-56 ثانية للصفحة. **الإصلاح: بوابة تهدئة عامة مشتركة** — أول 418/429 يوقف كل الدفعات فوراً (فشل سريع في أجزاء الثانية بدل 30-56 ثانية)، الصفحة تعود بما هو متوفر مع `has_more=true`، **والفجوات تُملأ تلقائياً في الطلبات التالية** لأن اكتشاف النواقص يعاد في كل طلب (كاش يُصلح نفسه).

### 3) قراءة parquet في كل طلب تمرير — أصبحت مرآة ذاكرة بتحقق mtime
كان كل طلب يقرأ ملف الكاش كامل من القرص ويعيد فرزه. الآن: القرص مرة واحدة، والطلبات التالية تقرأ من الذاكرة (تعيد القراءة فقط إذا تغيّر الملف بعد حفظ جديد).

### نتائج القياس النهائية (محلياً بعد الجولة)

| الحالة | قبل الجولة | بعد الجولة |
|---|---|---|
| صفحة 5000 شمعة (باردة، بلا حظر) | 22-56s | **0.1-0.4s** |
| نفس الصفحة (ساخنة) | ثوانٍ (قراءة كاملة من القرص) | **~0.2s (صفر IO)** |
| صفحة أثناء حظر Binance | 30-56s معلّقة + بيانات ناقصة صامتة | **<0.5s فورية + has_more صادق + ملء ذاتي لاحقاً** |

| تهيئة المزوّدين لكل طلب signals | BinanceProvider + CSV 5223 رمز في كل طلب | **مرة واحدة (singleton)** |

## 1) سبب مشكلتك بالضبط (لماذا كانت الحاويات تعيد التشغيل باستمرار؟)

```
asyncpg.exceptions.InvalidPasswordError: password authentication failed for user "trader"
RuntimeError: Database initialization failed; refusing to serve requests
```

**السبب الجذري:** حاوية Postgres تحفظ بياناتها في volume باسم `postgres_data`.
كلمة المرور `POSTGRES_PASSWORD` في `docker-compose.yml` تُطبَّق **فقط عند أول تهيئة لـ volume فارغ**.
عندك الـ volume أُنشئ سابقًا (تجارب سابقة / استيراد Neon) **بكلمة مرور مختلفة**، فأصبح هناك تعارض:

| المصدر | كلمة المرور المخزنة فعليًا في الـ volume |
|---|---|
| `docker-compose.yml` (الآن) | `trader_local_2024` |
| الـ volume القديم `postgres_data` (الواقع) | كلمة مرور أقدم مختلفة ❌ |

فيقفل Postgres الباب في وجه الباكند مهما أعدت التشغيل — لأن إعادة التشغيل لا تغيّر كلمة مرور مخزنة من قبل.

**الحل الذي نفّذته لك:** سكربت `heal-postgres.sql` يُنفَّذ من داخل حاوية Postgres نفسها
(قناة إدارية موثوقة لا تحتاج كلمة مرور) ويضبط المستخدم/القاعدة/كلمة المرور لتطابق `.env` —
**بدون حذف الـ volume وبدون فقدان أي بيانات** (الباك تستات والاستراتيجيات تبقى كما هي).

## 3) ماذا أصلحت في الكود؟ (تم اختباره فعليًا)

### أ) إصلاح جوهري في قسم العملات — `app/routers/market_data.py`
نقطة `/api/v1/market/historical/...` كانت تُعيد `start_date: null` و`end_date: null` لأزواج العملات
(عمود `time` بالملي ثانية لم يكن مُعترفًا به كمصدر تاريخ). بعد الإصلاح تُعاد تواريخ ISO حقيقية:

```
قبل:  {"row_count": 72, "start_date": null, "end_date": null}
بعد:  {"row_count": 72, "start_date": "2026-10-26T11:00:00", "end_date": "2026-10-29T10:00:00"}
```

### ب) ملف `.env` — كان بإعداد خاطئ للتشغيل عبر Docker
كان يحوي `DATABASE_URL=sqlite+aiosqlite:///./trading.db` (إعداد بيئة اختبار) بينما نظامك يعمل عبر
Docker + Postgres. أعيد ضبطه ليتطابق حرفيًا مع `docker-compose.yml`، وأضفت
`http://localhost:3018` و`http://127.0.0.1:3018` إلى `CORS_ORIGINS` (الفرونت عندك على 3018).

### ج) سكربتات الإصلاح الذاتي (جديدة)
`START-LOCAL.bat` + `FIX-DB.bat` + `heal-postgres.sql` — شرحها في القسم 2.

## 5) بنية الحزمة — ما الذي سينسجم مع ما عندك؟

```
backend/
├── START-LOCAL.bat          ← جديد: تشغيل كامل + إصلاح ذاتي
├── FIX-DB.bat               ← جديد: إصلاح قاعدة البيانات فورًا
├── heal-postgres.sql        ← جديد: سكربت الإصلاح
├── .env                     ← معدل: إعداد Docker الصحيح + CORS 3018
├── app/routers/market_data.py ← معدل: إصلاح التواريخ في قسم العملات
├── docker-compose.yml       ← كما هو (سليم)
├── Dockerfile               ← كما هو (سليم)
└── ... (باقي المشروع كاملًا مع بيانات الكاش التاريخية parquet)
```

الطريقة الأسهل للدمج: فك الضغط فوق المجلد القديم ووافق على الاستبدال.

## 6) إذا استمرت أي مشكلة (تشخيص في 30 ثانية)

```bat
docker compose ps                     هل backend يعيد التشغيل؟
docker compose logs backend --tail 50 ماذا تقول آخر الرسائل؟
FIX-DB.bat                            إصلاح كلمة المرور فورًا
curl http://localhost:8000/api/v1/health
```

إن فشل كل شيء وبذلت تعتيبًا (خيار أخير يفقد بيانات الـ volume فقط):
```bat
docker compose down -v
START-LOCAL.bat
```
(سيبدأ Postgres من جديد بكلمة المرور الصحيحة، والجداول تُنشأ تلقائيًا عند أول تشغيل.)
